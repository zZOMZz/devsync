## 背景与已定方向

最初的同步功能放在 `www_so_com` 内部，包含项目路径、目录排除、两份 `.env` 和公司代理等约定。用户认为耦合过深，已决定采用独立 CLI。

原业务仓库的 `develop` 和 `origin/develop` 中，内置工具的提交由用户撤回；本工具独立开发。业务项目通过一份 `sync.config.json` 接入，后续通用能力继续放在此仓库。历史业务分支不是继续开发 CLI 的工作目录。

已定方向：

1. 独立 CLI 优先，核心同步服务与终端交互分开。
2. 未来 VS Code 插件可调用相同 CLI/API，目前没有实现插件。
3. 本地是同步来源，第一版只支持本机到 Linux 开发机的单向复制。
4. 程序包按用户、版本和平台共享；各项目连接、凭据、锁和同步状态独立。
5. 项目目录及 `.env` 策略由规则文件表达；公司代理属于用户配置。
6. 业务项目无需 `package.json`，也无需复制同步脚本。

## 已实现

- `init`、`config`、`preview`、`sync`、`start`、`stop`、`status`，支持当前目录和 `--dir` / `-C`。
- SSH 别名发现、账号/端口默认值、远端主目录推导、分项验证和隐藏密码输入。
- 预览新增/覆盖/删除；首次接入或目标/规则变更后确认，并备份受影响的远端文件。
- 后台同步及密码重连；`stop` 只处理当前项目。
- `dashboard` 使用 Ink + React 管理已登记项目，Clack 继续处理配置和确认；本地要求 Node.js 22+，远端不需要 Node.js。
- 共享 Mutagen 缓存、跨进程下载锁、校验后启用、旧 `.sync/tools/` 复用。
- 项目规则与个人连接配置分开；默认排除 `.env*`，可显式允许具体文件。
- JSON 输出和可导入的核心 API。
- Web/PHP 与 Python 两种项目规则示例。

源码入口为 [CLI](../src/cli.mjs)、[服务层](../src/service.mjs)、[规则](../src/rules.mjs) 和[公共导出](../src/index.mjs)。

## 接续工作

先读取[架构](architecture.md)和[优化候选](roadmap.md)，选择一个具体问题复现，再做有针对性的修改。建议先处理服务与接口边界，再完善诊断与性能。优化候选不是已经确认要全部实现的需求。

继续开发时保留这些行为约束：

- `preview` 会暂停自动同步，但不写远端源码。
- `status` 不启动 Mutagen daemon。
- 原本处于自动模式时，`sync` 成功后保持自动模式；普通单次同步结束暂停。
- 取消新的配置或同步确认后，不启动未经确认的目标。
- 预览筛选规则与实际 Mutagen 传输规则一致。
- 缓存清理或升级不能破坏其他项目仍在使用的版本。
- 密码和运行状态只存于私有位置，不进入项目公共规则、日志或程序包。
